# ESP32-S3 line follower: MQTT, persistence, and tuning dashboard plan

Status: Phases 0–4 software are implemented. Latest checks: 28/28 native firmware tests, ESP32-S3 build, 20/20 backend tests (including authenticated local-Mosquitto integration and broker-recovery coverage), 7/7 frontend data tests/build, and 5/5 provisioning tests pass. The dashboard was browser-checked at desktop and phone widths with synthetic MQTT data. Phase 4 is the final planned feature phase; actual ESP32 provisioning, timing, PID persistence/power-cycle and track tests remain the final physical acceptance and are not verified. The existing firmware is a PlatformIO Arduino project; do not replace it with a server-side control loop. The robot must continue to steer locally if Wi-Fi, Mosquitto, the dashboard, or SQLite is down.

Phase 0 progress: sensor readings use one sampled mask and the tracking/corner/loss FSM is hardware-independent. Phase 1 adds schema-versioned Preferences/NVS PID and Wi-Fi/Mosquitto settings plus bounded USB serial provisioning. Phase 2 adds pinned control/network/storage tasks, MQTT 3.1.1, bounded queues, telemetry, versioned PID commands/acks and debounced NVS writes. Phase 3 adds authenticated local Mosquitto templates/ACLs, a Hono MQTT-to-HTTP/SSE bridge, SQLite persistence, protected PID command API, retention, and integration tests. Host tests/builds do not verify physical behavior: no robot was detected for upload; board/wiring safety, NVS power-cycle behavior, ESP32 broker reconnection, control jitter, wheels-up behavior and track behavior remain physically unverified.

## 1. What is in this repository now

- `hardware/platformio.ini`: `esp32-s3-devkitc-1`, Arduino, C++11; pinned `256dpi/MQTT@2.5.3` and `ArduinoJson@6.21.5`. Native Unity tests cover the hardware-independent PID, sensor, control-step, provisioning and MQTT protocol code. ESP32 Preferences/NVS holds device/PID data. `backend/` contains the Node/Hono bridge and SQLite store; `frontend/` contains the React/Vite telemetry and PID dashboard.
- `hardware/include/config.h`: five digital HW-871 sensors on GPIO 36–40, active-low; TB6612FNG motor pins 11–17; compiled PID fallback gains `Kp=12.5, Ki=1.0, Kd=0.15`; base PWM 75; 10 ms control period; 50-cycle (~500 ms) missing-line grace; corner pivot timeout 1500 ms.
- `hardware/src/line_sensor.cpp`: samples each of the five digital inputs once per tick and returns a `SensorReading` whose mask, line-presence flag, and position are derived from that same sample.
- `hardware/src/main.cpp`: loads NVS and keeps motors in standby during a five-second USB provisioning window (indefinitely if network settings are missing), then starts the FreeRTOS tasks. `controlTask` owns sensors, PID/FSM and motors on core 1; `networkTask` owns Wi-Fi/MQTT on core 0; `storageTask` writes PID blobs off the control task. Serial diagnostics are not emitted from the real-time control path.
- `hardware/src/controller.cpp`: PID with integral clamp, derivative on error and output clamp; validated runtime gain updates reset controller history. Derivative filtering and saturation-aware anti-windup remain absent. Twenty-eight native tests cover PID bounds/configuration, all sensor masks, tracking/corner/loss FSM behavior, provisioning and MQTT protocol encoding/validation.
- `hardware/src/motor_driver.cpp`: `analogWrite` PWM and TB6612 direction/standby. Stops by setting PWM to zero; direction pins remain as previously set. There is no explicit connectivity/safety watchdog, and no identified PWM frequency/resolution contract.
- The backend and frontend run on the local host, never on the ESP32. Vite proxies API/SSE traffic to Hono; the browser never connects directly to MQTT.

## 2. Architecture and boundaries

```text
5 digital IR inputs -> ESP32-S3 control task (10 ms, core 1) -> TB6612/motors
                           | latest telemetry / PID command queue
                           v
                ESP32-S3 Wi-Fi/MQTT task (core 0)
                           | MQTT over LAN (TCP 1883)
                     local Mosquitto broker
                           |
             Node.js Hono bridge + SQLite (local host)
                           | HTTP + Server-Sent Events (SSE)
                  React/Vite browser dashboard
```

- MQTT carries bounded telemetry and commands; the broker only routes messages. SQLite is on the local host and stores telemetry/PID history, not on ESP32 flash. A small Hono service bridges MQTT to HTTP/SSE because browsers cannot speak raw MQTT/TCP; no Mosquitto WebSocket listener or browser-held broker password is needed.
- ESP32-S3 has two application cores but shares memory and Wi-Fi system work; pinning tasks does **not** isolate radio scheduling completely. Keep motor/control decisions independent of networking, JSON, SQLite, HTTP and flash I/O. Use only the board resources actually verified in hardware.
- Select one stable robot ID (for example `linebot-01`) and one broker LAN address/hostname. Device and host must reach each other on the same permitted LAN. Resolve hostname before production if mDNS/DNS is unreliable; never compile a developer laptop's `localhost` into the firmware (`localhost` on ESP32 means the ESP32 itself).

## 3. Protocol contract (document and implement consistently)

Use MQTT 3.1.1 with an authenticated device client, unique client ID `linebot-<chip-id>`, and `robots/<id>/...` topics. The firmware pins `256dpi/MQTT` 2.5.3 (QoS 1 publish/subscribe and last-will support) and ArduinoJson 6.21.5; both are compile-checked against the current ESP32 Arduino platform. Payloads are capped at 512 bytes and fixed buffers are sized accordingly. Never use `localhost` or `.local` for the broker from the ESP32; provision a LAN IPv4 address or a DNS hostname resolvable by the board. Avoid unbounded `String` allocation in the 10 ms control task.

| Topic | Direction | QoS / retained | Purpose |
| --- | --- | --- | --- |
| `robots/<id>/telemetry` | device -> broker | 0 / no | sampled sensor/control telemetry, e.g. 10–20 Hz, never every control tick |
| `robots/<id>/status` | device -> broker | 1 / yes | `online` at connect, MQTT last-will `offline` on ungraceful disconnect; include protocol version |
| `robots/<id>/pid/set` | bridge -> device | 1 / **no** | full PID candidate with unique request ID and `baseRevision`; apply only against the current revision and never retain commands |
| `robots/<id>/pid/state` | device -> broker | 1 / yes | effective gains, monotonically increasing device revision, persistence state; publish on connect and after change/save |
| `robots/<id>/pid/ack` | device -> broker | 1 / no | request ID, accepted/rejected reason, applied revision, and later persisted result |

Define explicit JSON schema version `v: 1`. Telemetry includes `robotId`, a boot/session ID, monotonically increasing sequence number, `uptimeMs`, sensor `mask` (0..31), position/error (null when no line), controller correction, commanded left/right PWM, FSM mode (`track`/`pivot`/`lost`), measured `dtMs`, PID revision, overwritten telemetry-frame count and dropped ack count. Backend adds `received_at` UTC; `(bootId, seq)` provides deduplication and ordering. PID set JSON is `{v, requestId, baseRevision, kp, ki, kd}`; the device checks request ID and revision, applies only on the control-task tick, and stores the last request ID with the PID record for QoS 1 redelivery after reboot. PID state reports effective gains/revision/request ID plus `persisted`; ack statuses distinguish `applied`, `persisted`, `rejected`, and `failed`. Do not log credentials. Bound strings, validate JSON types/finite numbers/size/gain ranges, and never retain PID commands. Current gain limits are derived from actuator/sensor numeric bounds, not bench-proven stability limits. Backend serves latest device-reported state, not the last requested values. No remote direct motor-speed or movement command in the first milestone.

## 4. Implementation phases (ordered, with completion checks)

### Phase 0 — hardware baseline and safety audit

1. Record exact ESP32-S3 module/DevKitC revision, flash/PSRAM variant, HW-871 output voltage, TB6612 power/ground wiring, motor polarity, USB mode, and GPIO exposure. Confirm GPIO36–40 are actually usable on **this** S3 variant (some flash/PSRAM configurations or board routing constrain pins); check 3.3 V logic levels and common ground before connecting 5 V sensor outputs. Check motor supply and brownout behavior under Wi-Fi transmission; add decoupling/level shifting as required by measured hardware. Do not assume a generic S3 pin map proves a particular board is safe.
2. Establish baseline: from `hardware/` run `python -m platformio test -e native` and `python -m platformio run -e esp32s3`; these pass in the current environment. Photograph/record a bench test with wheels lifted and a track trial when the actual robot is connected; that physical baseline remains pending.
3. Refactor `LineSensor` to sample exactly once per tick into a value object `{mask, hasLine, position}` computed from that same mask. Extract corner/loss FSM from `main.cpp` into a testable control-step class with explicit input and motor-command outputs; preserve existing corner behavior until regression tests pass. Add host tests for all 32 masks, left/right/center cluster classification, blackout confirmation, pivot reacquisition sides, timeouts and line loss. Change grace/timeout values only after measuring stopping distance and safe test-track behavior: the current 500 ms coast on last motor command may be unsafe near a table edge.
4. Verify PWM frequency/resolution on the installed Arduino-ESP32 version; set them explicitly with supported LEDC APIs if needed, avoid dynamic PWM channel collisions, and check TB6612 standby and zero-speed behavior. Add a physical kill switch or reliable power cutoff; Wi-Fi/MQTT must never be the sole emergency stop. Track scheduling jitter, motor commands and serial output during bench tests. Avoid `Serial.print` in the real-time path (send event codes to the lower-priority task instead).

Acceptance: existing track/pivot/loss behavior is covered by native tests and checked on wheels-up hardware before networking is introduced.

### Phase 1 — no-rebuild device provisioning and safe persisted PID

1. Create `hardware/include/pid_config.h`, `hardware/src/pid_storage.cpp` (or equivalent) using Arduino ESP32 `Preferences`/NVS. Store `{schemaVersion, kp, ki, kd, revision}` under a namespaced key; on first boot, absent/incompatible/nonfinite/out-of-range values fall back to `config.h` defaults. Validate on read and before write, verify write return value, and only mark persisted after successful write. Reset gains via a deliberate USB provisioning command; document NVS erase/recovery. NVS has limited flash write endurance: coalesce edits, save after a short quiet interval (e.g. 2 s), flush when practical, and warn UI that recently applied but unpersisted values may be lost on power-off.
2. `Preferences` also holds `wifiSsid`, `wifiPassword`, `mqttHost`, `mqttPort`, `mqttUser`, `mqttPassword`, `robotId` (separate namespace). On first boot with missing config, keep motors in standby and accept provisioning over USB serial via a small local `tools/provision.py` (`getpass` for secrets, pyserial, explicit ACK and readback of **nonsecret** fields). Provide reprovision/reset while motors disabled; validate length/port and never print passwords. Updating SSID/password/host needs **no rebuild**. C++ `.env` at compile time would bake secrets into firmware and force reflashing, so do **not** use a firmware `.env` for changeable Wi-Fi credentials. NVS is device-local runtime storage, but default NVS is not encrypted. USB serial provisioning is also cleartext; hex encoding is for framing only, so trust the host/cable and never capture or forward the provisioning session. Document physical-access risk and consider NVS encryption/secure boot if the threat model demands it. Wi-Fi SSID/password and MQTT credentials are distinct.
3. Keep host-only secrets in ignored `backend/.env` (from `backend/.env.example`) and create ignored `infra/mosquitto/passwd`, `infra/mosquitto/mosquitto.conf.local`, `backend/data/`, and other generated files as appropriate. Commit templates and instructions but never real passwords, database, logs, or dump files. Add explicit `.gitignore` entries (including nested `.env*` with template exceptions), run `git check-ignore` on sample secret paths and audit staged diffs before commit. Never log/return credential fields through HTTP.

Acceptance: changing Wi-Fi or broker credentials via USB and rebooting reconnects without recompiling; PID survives power cycle, corrupted/unsupported NVS falls back safely, and no secret or database is tracked.

### Phase 2 — ESP32-S3 tasking and MQTT

1. Make setup initialize serial/provisioning, NVS, sensors/motors and queues before task creation. Create a periodic `controlTask` pinned to core 1 (`xTaskCreatePinnedToCore`, priority higher than network; `vTaskDelayUntil` / FreeRTOS ticks for cadence, `micros()` or `esp_timer_get_time()` for measured PID `dt`, bounded dt after stalls). Do not assume Arduino's default `loopTask` is already on a suitable core: check `CONFIG_ARDUINO_RUNNING_CORE` and choose whether `loop()` is idle with a proper delay or performs provisioning orchestration; never run a second competing control loop. Confirm scheduler tick resolution supports 10 ms. Only control task owns `LineController`, FSM, `LineSensor`, and `MotorDriver`.
2. Create lower-priority `networkTask` pinned to core 0 for `WiFi` station reconnect, MQTT connect/subscribe/`loop()`, bounded JSON encoding/decoding and throttled telemetry. Keep MQTT client ownership entirely in this task: callback validates and writes a complete candidate to a length-1 command queue; do **not** mutate PID, motor pins or NVS from MQTT callbacks. Control task consumes command at a tick boundary and sends ack/state via queues. Latest-value telemetry mailbox (length 1, `xQueueOverwrite`) keeps control nonblocking and counts overwritten/dropped snapshots; separate small bounded ack/event queue with explicit overflow behavior. Restrict queue element size and task stacks, inspect high-water marks and heap during runtime.
3. For persistence use a low-priority storage task (core 0) or a specifically bounded deferred operation outside `controlTask`: debounce and write NVS, then queue persistence result for `networkTask`. Serialize access to shared settings, use POD queue messages / immutable copies instead of a globally shared mutable `String`; never hold mutexes while doing Wi-Fi, flash, or `Serial` I/O. A briefly-blocked broker or flash write must not defer motor updates.
4. MQTT/Wi-Fi use timeouts and capped exponential reconnect backoff; disable Wi-Fi power save if latency measurements justify it (measure power impact). Keep robot locally autonomous after broker loss; expose disconnect and bounded telemetry drop counts. Define a distinct safe state after boot/no line; do not energize motors merely because MQTT connects. Publish retained status with a last will and the current effective PID state after reconnect; telemetry stays nonretained. Limit TCP connect/publish blocking and measure control deadline misses during outages/reconnections; if deadline fails, restructure network work rather than increasing control period silently.
5. The firmware pins `256dpi/MQTT@2.5.3` because it supports synchronous MQTT 3.1.1 publish/subscribe at QoS 1 and last wills; ArduinoJson `6.21.5` is pinned for bounded JSON parsing/serialization. Set receive/write buffers explicitly and keep payload/document sizes within measured bounds. Do not publish, subscribe, or access the client from its message callback; callbacks only validate and enqueue.

Acceptance: wheels-up and track tests show 10 ms control cadence with quantified worst-case jitter during Wi-Fi startup, broker outage and NVS save; motors continue tracking offline; reconnects do not duplicate persistent commands; PID apply/ack/save work without control-task blocking.

### Phase 3 — local broker, minimal bridge, SQLite

1. Add `infra/mosquitto/mosquitto.conf.example`, local setup instructions and an ignored actual config/password file. The template binds loopback by default; before ESP32 use, edit the local config to bind only the broker host's LAN IPv4 address on port 1883, set backend `MQTT_URL` to that address, and restrict the firewall to the robot/backend subnet. Set `allow_anonymous false`, `password_file`, retained persistence and unique credentials for device and backend. Use Mosquitto ACLs: each device can publish only its own `telemetry/status/pid/state/pid/ack` and subscribe only to its `pid/set`; backend can subscribe to telemetry/state/ack and publish `pid/set`. Never expose the listener to the internet. The current firmware uses plain MQTT, acceptable only on a trusted private network; use TLS/VPN or a stronger boundary for untrusted or remote access.
2. Add `backend/` as a small Node.js service: Hono for HTTP, `mqtt.js` for the single backend MQTT connection, `better-sqlite3` for a local file DB (pin versions supported by the chosen Node LTS; current host has Node v20.16.0), schema migrations and prepared statements. Prefer simple synchronous bounded inserts in a limited MQTT handler; if disk latency affects ingest, add a bounded batch writer. Enable WAL, busy timeout, indices and retention/pruning so a high-rate stream cannot grow forever. Schema example: `telemetry(robot_id, boot_id, seq, received_at, uptime_ms, mask, position, error, correction, left_pwm, right_pwm, mode, dt_ms, pid_revision)` with unique `(robot_id, boot_id, seq)`; `pid_changes(request_id PRIMARY KEY, robot_id, requested_at, kp, ki, kd, status, applied_revision, updated_at, reason)`; status/latest PID state may be maintained in a small table or derived from state/ack events. Never treat an HTTP publish success as device application or persistence.
3. API contract: `GET /api/robots/:id/latest`, `GET /api/robots/:id/telemetry?limit=&cursor=`, `GET /api/robots/:id/pid`, `POST /api/robots/:id/pid` (JSON full gains, validates numeric ranges, creates request ID, returns `202` + ID/pending), `GET /api/robots/:id/events` (SSE: telemetry, status, pid state/ack). Use stable composite keyset cursors so ties in server receive timestamps are not skipped; bound queries, cap limits, and apply retention. A device ack advances `pending -> applied -> persisted` or `rejected/failed`; reconnect reconcile via `pid/state`, never infer success from command delivery. Bind HTTP to loopback only; protect PID writes with the configured admin bearer token and origin checks. For remote browser access, use a TLS/authenticated reverse proxy or VPN rather than exposing this plain-HTTP service. SSE uses bounded clients/backpressure, heartbeat and cleanup on disconnect; browser polling remains an acceptable fallback.
4. Validate robot ID allowlist, payload schema/version/size, finite floats and timestamps on ingress. Use `.env.example` for `MQTT_URL`, `MQTT_USERNAME`, `MQTT_PASSWORD`, `DB_PATH`, `HTTP_HOST`, `HTTP_PORT`, `ADMIN_TOKEN`, `ALLOWED_ORIGINS`, `ROBOT_IDS`, and `RETENTION_DAYS` (no secret defaults). For remote browsers, restrict allowed origins and use HTTPS/reverse proxy or VPN; the MVP can bind the UI/API to `127.0.0.1` on the host and run the dashboard there. Include Mosquitto/Node startup and health checks in README; do not require Docker.

Acceptance: publish synthetic test telemetry through local broker, read identical `(robot_id, boot_id, seq)` row back from SQLite/API, reject duplicates/malformed data, verify ack status progression and broker outage/recovery. Test secret rejection and unauthenticated PID write denial.

Implementation update: the Mosquitto example config and per-robot ACL are exercised by an integration test that starts a temporary authenticated broker. The backend validates bounded telemetry/status/event/PID payloads; stores deduplicated telemetry and control events plus latest status/PID state and PID command lifecycle in SQLite; exposes health/latest/history/PID/SSE endpoints; and only accepts PID writes with an admin bearer token and allowed browser origin. HTTP binds are validated as loopback-only and Host headers are restricted to loopback names/addresses to block DNS rebinding. PID command outcomes are monotonic (`pending -> applied -> persisted`, with `failed`/`rejected` terminal) so late ACKs cannot roll status backward or broadcast stale events. The Mosquitto template is also loopback-only until explicitly changed to the broker's trusted LAN interface. Tests verify telemetry insert/deduplication, PID command delivery as QoS 1 non-retained, applied-to-persisted reconciliation, reconnect after broker restart, cursor paging across equal timestamps, and graceful HTTP/database shutdown. API route tests verify unauthorized/origin-denied/oversized PID writes, DNS-rebinding Host rejection and the real Node HTTP adapter health route. MQTT integration uses synthetic clients rather than a physical ESP32; actual device MQTT, NVS, and control continuity remain unverified.

## 6. Open decisions to resolve on the bench, not by guessing

- Exact ESP32-S3 variant, available GPIOs, sensor logic voltage and motor wiring; whether GPIO36–40 conflict with this board's memory/PSRAM routing.
- Actual max safe PID gains, lost-line grace distance, pivot reacquisition threshold, control-stack size, MQTT payload/buffer size, telemetry rate and max dashboard retention, based on measured results.
- Default deployment is host-local-only: Hono binds to loopback and the Vite dev server proxies API requests locally. If another device must use the dashboard, place a TLS/authenticated reverse proxy or VPN in front of the local service; do not bind the plain-HTTP bridge directly to the LAN.
