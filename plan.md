## 1. What is in this repository now

- `hardware/platformio.ini`: `esp32-s3-devkitc-1`, Arduino, C++11; pinned `256dpi/MQTT@2.5.3` and `ArduinoJson@6.21.5`. Native Unity tests cover the hardware-independent PID, sensor, control-step, provisioning and MQTT protocol code. ESP32 Preferences/NVS holds device/PID data. `backend/` contains the Node/Hono bridge and SQLite store; `frontend/` contains the React/Vite telemetry and PID dashboard.
- `hardware/include/config.h`: five digital HW-871 sensors on GPIO 36–40, active-low; TB6612FNG motor pins 11–17; compiled PID fallback gains `Kp=12.5, Ki=1.0, Kd=0.15`; base PWM 75; 10 ms control period; 50-cycle (~500 ms) missing-line grace; corner pivot timeout 1500 ms.
- `hardware/src/line_sensor.cpp`: samples each of the five digital inputs once per tick and returns a `SensorReading` whose mask, line-presence flag, and position are derived from that same sample.
- `hardware/src/main.cpp`: loads NVS and keeps motors in standby during a five-second USB provisioning window (indefinitely if network settings are missing), then starts the FreeRTOS tasks. `controlTask` owns sensors, PID/FSM and motors on core 1; `networkTask` owns Wi-Fi/MQTT on core 0; `storageTask` writes PID blobs off the control task. Serial diagnostics are not emitted from the real-time control path.
- `hardware/src/controller.cpp`: PID with integral clamp, low-pass derivative and conditional anti-windup, plus output clamp; validated runtime gain updates reset controller history. Thirty-five native tests cover PID bounds/configuration, all sensor masks, tracking/corner/loss FSM behavior, provisioning and MQTT protocol encoding/validation.
- `hardware/src/motor_driver.cpp`: `analogWrite` PWM and TB6612 direction/standby. Stops by setting PWM to zero; direction pins remain as previously set. There is no explicit connectivity/safety watchdog, and no identified PWM frequency/resolution contract.
- The backend and frontend run on the local host, never on the ESP32. Vite proxies API/SSE traffic to Hono; the browser never connects directly to MQTT.

## 2. Architecture and boundaries

```text
5 digital IR inputs -> ESP32-S3 control task (10 ms, core 1) -> TB6612/motors
                           | latest telemetry / PID command queue
                           v
                ESP32-S3 Wi-Fi/MQTT task (core 0)
                           | MQTT over LAN (TCP 1883)
                     local Mosquitto broker
                           |
             Node.js Hono bridge + SQLite (local host)
                           | HTTP + Server-Sent Events (SSE)
                  React/Vite browser dashboard
```

- MQTT carries bounded telemetry and commands; the broker only routes messages. SQLite is on the local host and stores telemetry/PID history, not on ESP32 flash. A small Hono service bridges MQTT to HTTP/SSE because browsers cannot speak raw MQTT/TCP; no Mosquitto WebSocket listener or browser-held broker password is needed.
- ESP32-S3 has two application cores but shares memory and Wi-Fi system work; pinning tasks does **not** isolate radio scheduling completely. Keep motor/control decisions independent of networking, JSON, SQLite, HTTP and flash I/O. Use only the board resources actually verified in hardware.
- Select one stable robot ID (for example `linebot-01`) and one broker LAN address/hostname. Device and host must reach each other on the same permitted LAN. Resolve hostname before production if mDNS/DNS is unreliable; never compile a developer laptop's `localhost` into the firmware (`localhost` on ESP32 means the ESP32 itself).

## 3. Protocol contract (document and implement consistently)

Use MQTT 3.1.1 with an authenticated device client, unique client ID `linebot-<chip-id>`, and `robots/<id>/...` topics. The firmware pins `256dpi/MQTT` 2.5.3 (QoS 1 publish/subscribe and last-will support) and ArduinoJson 6.21.5; both are compile-checked against the current ESP32 Arduino platform. Payloads are capped at 512 bytes and fixed buffers are sized accordingly. Never use `localhost` or `.local` for the broker from the ESP32; provision a LAN IPv4 address or a DNS hostname resolvable by the board. Avoid unbounded `String` allocation in the 10 ms control task.

| Topic | Direction | QoS / retained | Purpose |
| --- | --- | --- | --- |
| `robots/<id>/telemetry` | device -> broker | 0 / no | sampled sensor/control telemetry, e.g. 10–20 Hz, never every control tick |
| `robots/<id>/status` | device -> broker | 1 / yes | `online` at connect, MQTT last-will `offline` on ungraceful disconnect; include protocol version |
| `robots/<id>/pid/set` | bridge -> device | 1 / **no** | full PID candidate with unique request ID and `baseRevision`; apply only against the current revision and never retain commands |
| `robots/<id>/pid/state` | device -> broker | 1 / yes | effective gains, monotonically increasing device revision, persistence state; publish on connect and after change/save |
| `robots/<id>/pid/ack` | device -> broker | 1 / no | request ID, accepted/rejected reason, applied revision, and later persisted result |

Define explicit JSON schema version `v: 1`. Telemetry includes `robotId`, a boot/session ID, monotonically increasing sequence number, `uptimeMs`, sensor `mask` (0..31), position/error (null when no line), controller correction, commanded left/right PWM, FSM mode (`track`/`pivot`/`lost`), measured `dtMs`, PID revision, overwritten telemetry-frame count and dropped ack count. Backend adds `received_at` UTC; `(bootId, seq)` provides deduplication and ordering. PID set JSON is `{v, requestId, baseRevision, kp, ki, kd}`; the device checks request ID and revision, applies only on the control-task tick, and stores the last request ID with the PID record for QoS 1 redelivery after reboot. PID state reports effective gains/revision/request ID plus `persisted`; ack statuses distinguish `applied`, `persisted`, `rejected`, and `failed`. Do not log credentials. Bound strings, validate JSON types/finite numbers/size/gain ranges, and never retain PID commands. Current gain limits are derived from actuator/sensor numeric bounds, not bench-proven stability limits. Backend serves latest device-reported state, not the last requested values. No remote direct motor-speed or movement command in the first milestone.

### Phase 2 — ESP32-S3 tasking and MQTT

1. Make setup initialize serial/provisioning, NVS, sensors/motors and queues before task creation. Create a periodic `controlTask` pinned to core 1 (`xTaskCreatePinnedToCore`, priority higher than network; `vTaskDelayUntil` / FreeRTOS ticks for cadence, `micros()` or `esp_timer_get_time()` for measured PID `dt`, bounded dt after stalls). Do not assume Arduino's default `loopTask` is already on a suitable core: check `CONFIG_ARDUINO_RUNNING_CORE` and choose whether `loop()` is idle with a proper delay or performs provisioning orchestration; never run a second competing control loop. Confirm scheduler tick resolution supports 10 ms. Only control task owns `LineController`, FSM, `LineSensor`, and `MotorDriver`.
2. Create lower-priority `networkTask` pinned to core 0 for `WiFi` station reconnect, MQTT connect/subscribe/`loop()`, bounded JSON encoding/decoding and throttled telemetry. Keep MQTT client ownership entirely in this task: callback validates and writes a complete candidate to a length-1 command queue; do **not** mutate PID, motor pins or NVS from MQTT callbacks. Control task consumes command at a tick boundary and sends ack/state via queues. Latest-value telemetry mailbox (length 1, `xQueueOverwrite`) keeps control nonblocking and counts overwritten/dropped snapshots; separate small bounded ack/event queue with explicit overflow behavior. Restrict queue element size and task stacks, inspect high-water marks and heap during runtime.
3. For persistence use a low-priority storage task (core 0) or a specifically bounded deferred operation outside `controlTask`: debounce and write NVS, then queue persistence result for `networkTask`. Serialize access to shared settings, use POD queue messages / immutable copies instead of a globally shared mutable `String`; never hold mutexes while doing Wi-Fi, flash, or `Serial` I/O. A briefly-blocked broker or flash write must not defer motor updates.
4. MQTT/Wi-Fi use timeouts and capped exponential reconnect backoff; disable Wi-Fi power save if latency measurements justify it (measure power impact). Keep robot locally autonomous after broker loss; expose disconnect and bounded telemetry drop counts. Define a distinct safe state after boot/no line; do not energize motors merely because MQTT connects. Publish retained status with a last will and the current effective PID state after reconnect; telemetry stays nonretained. Limit TCP connect/publish blocking and measure control deadline misses during outages/reconnections; if deadline fails, restructure network work rather than increasing control period silently.

## 7. Follow-on plan: robust line tracking, loss recovery, and sharp turns

Status: software-side changes are implemented as summarized in 7.5. The symptoms (oscillation, straight-line offset, loss on a white track, poor turns above 90 degrees) still need a physical sensor trace and measured wheel response. Treat the analysis below as hypotheses, not proven hardware diagnoses. Gains, base speed, pivot PWM/timeout and line-loss grace remain untuned until the diagnostic baseline is recorded.

### 7.1 Baseline behavior before hardening and likely failure mechanisms

This subsection records the pre-hardening behavior that motivated the changes; see 7.5 for what has since changed.

- **The feedback signal is coarse and uncalibrated.** `LineSensor::read()` samples five digital pins and applies one global active-low setting (`hardware/src/line_sensor.cpp:11-20`, `hardware/include/config.h:9-14`). `sensorReadingFromMask()` turns active bits into the unweighted mean of sensor indices 0–4 (`hardware/src/sensor_reading.cpp:3-23`). The firmware has no per-channel reflectance values, threshold-margin measurements, debounce/hysteresis policy, or software calibration. A one-bit transition can move the measured position abruptly; different sensor thresholds and mounting offsets are treated as if identical.
- **Oscillation is plausibly amplified by discrete position changes and the raw derivative.** The PID differentiates error directly without filtering (`hardware/src/controller.cpp:14-35`). At the configured 10 ms period and `Kd=0.15`, a one-sensor-unit error step contributes 15 PWM from D alone; a four-unit jump contributes 60 PWM before P, against a 120 PWM correction limit. The error can span -2..+2 with five sensors, so a large jump is possible after a sudden mask change. `Kp=12.5` adds another 12.5 PWM per error unit. This can produce twitching or saturation, depending on actual sensor transitions and motion. These figures explain sensitivity; they do not prove the observed oscillation is caused by gains.
- **Straight-line bias may be mechanical or sensor-centering error, not simply insufficient Ki.** Both wheels use the same `BASE_SPEED=75`, with no measured per-wheel trim (`hardware/include/config.h:16-37`). Sensor order, sensor bar centering, motor polarity, wheel friction, battery voltage and track alignment are not calibrated in software. The integral is clamped to ±10 error-seconds and `Ki=1`, so its maximum contribution is ±10 PWM; that may be too little to cancel a real motor mismatch. Conversely, increasing Ki before checking those causes can create windup and worsen oscillation. There is no saturation-aware anti-windup.
- **White paper/board versus ceramic is an optical contrast question, not a color-name rule.** The code sees only five thresholded bits. A reflective IR sensor responds to returned infrared light, not the surface's visible color; the TCRT5000 emitter is near 950 nm, and its response varies with distance/geometry.[3] Thus visible-black tape can still be a weak IR contrast against a particular white or glossy surface, and a different ceramic/tape combination may cross the module's threshold more reliably. The exact HW-871 board revision, its comparator/potentiometer arrangement, output polarity, sensor height and surface reflectance are not confirmed. If the telemetry mask does not change reliably when each sensor is moved from substrate to line, the FSM cannot recover information the digital sensor did not report.
- **The line-loss behavior can look like “keeps going, then suddenly stops.”** After a no-sensor mask with no recent corner, `ControlStep` returns `MotorAction::Hold` for 50 cycles (~500 ms), then `Stop` (`hardware/src/control_step.cpp:88-109`; `hardware/include/config.h:40-43`). `applyMotorOutput()` returns immediately for `Hold`, so the motor driver keeps its prior PWM; it does not coast (`hardware/src/control_task.cpp:26-38`). The config comment calls this coasting, but it is active retention of the last drive command. The output defaults left/right speeds to zero, and telemetry records those fields, so it can report zero while the hardware is still holding the prior PWM (`hardware/src/control_step.cpp:49-61`, `hardware/src/control_task.cpp:179-195`). After the grace interval it stops and has no deliberate bounded search strategy; it only resumes when a line is sampled again. This is a specific code-level explanation for delayed stop, but the cause of the original sensor blackout still needs measurement.
- **The >90-degree path is an open-loop special case.** Tracking declares a corner candidate when a contiguous run of at least three sensors is detected; if the mask then becomes zero within five control cycles (~50 ms), it starts a pivot (`hardware/src/control_step.cpp:15-47, 115-135`). Direction comes from the run's side or a smoothed recent error. Pivoting commands a fixed opposite-wheel PWM (`CORNER_PIVOT_SPEED=90`) until a single qualifying sensor position is seen, or a 1500 ms timeout stops it (`hardware/src/control_step.cpp:145-179`, `hardware/include/config.h:45-53`). It does not measure yaw, wheel travel, or turn angle; it does not require several stable reacquisition samples. A gradual <90-degree bend can remain inside ordinary tracking, while a sharper >90-degree corner can lose all sensors and rely on this fixed-speed timed pivot. A wide line can also activate three sensors on a straight, so “three active” is not by itself proof of a corner.
- **One-sample loss resets PID history.** The first zero mask resets the controller before the grace period (`hardware/src/control_step.cpp:98-100`). This discards derivative/integral history even if the zero was a one-cycle dropout, then normal tracking resumes from reset when a sensor returns. The corner direction estimate is a low-pass `approachBias_`, not a line-loss trajectory estimate, and may lag a fast approach.

### 7.2 Comparison with common line-follower practice

- A common sensor-array baseline calibrates each channel over the actual line and background, normalizes reflectance, and estimates a monotonic weighted line position.[1] Some line-position APIs also retain the last-seen side when the line vanishes, which is useful for recovery direction.[4] The current five-bit mask plus equal-weight index average is a simpler binary baseline. It can work on a stable, high-contrast track, but it cannot recover analog confidence or adapt digitally to different per-channel thresholds. If this board exposes only comparator outputs, calibration must be mechanical (threshold pots, height, polarity) or the sensor hardware must change.
- A common controller uses line-position error to form differential left/right motor corrections, then tunes at a conservative base speed and raises speed gradually. Pololu's examples use calibrated line position with PD as a typical starting point, note that the gains depend on the robot, and describe integral as often unnecessary for line following.[1][2] This project already uses the same broad feedback structure, but applies an unfiltered derivative to quantized data, has no separate left/right base trim, and has not been physically tuned. PID is not inherently superior to PD here; use integral only for measured persistent bias after sensor and motor calibration.
- Sharp turns need enough sensor coverage, tuned speed/gains, and a defined recovery policy; whether normal tracking can handle them depends on the chassis and course. For comparison, Pololu's five-sensor 3pi+ example reports sharp-90-degree performance on its tested robot, but it calibrates sensors and uses motor/course-specific speed and PD settings.[5] The current code has a distinct pivot state, but its trigger is a short cluster-then-blackout heuristic and its actuation is fixed-time/open-loop. With no wheel encoders or IMU confirmed in this build, a timed pivot cannot guarantee a particular >90-degree heading; it must be bounded and bench-validated, or supplemented with heading feedback if repeatable turn angle is required.

### 7.3 Implementation sequence

#### Step A — capture a safe, useful baseline before changing control

1. Keep the wheels lifted or motor standby forced low. Add a sensor-diagnostic mode that displays each input bit (left-to-right), mask, line-present decision, position, and active-low interpretation without enabling motors. Do not print synchronously from the 10 ms control task; use a low-priority diagnostic path or a bounded rate.
2. On the actual track materials, record a per-channel matrix for: sensor over the line, over the background, straddling an edge, and at the installed height/angle. Repeat on the white surface and ceramic under the same lighting. Confirm each channel changes cleanly, the five bits are in physical left-to-right order, and the expected line polarity matches `SENSOR_LINE_ACTIVE_LOW`. Inspect/tune the module's threshold controls only if the installed board has them; record the final setting. Check supply/logic levels and common ground before changing GPIOs.
3. Capture live telemetry on a slow straight and the problematic turns: `mask`, position, error, correction, commanded PWM, mode, `dtMs`, and transition events. First fix telemetry so `Hold` reports the effective held motor command/action rather than zeros. This data distinguishes sensor dropout, control saturation, wrong turn direction and scheduler delay.
4. Verify motor sign and polarity with wheels lifted: a measured line-right error must command a right turn. Then measure left/right forward response separately at low PWM and record drift, wheel mismatch and sensor-bar center offset. Do not infer these from code defaults.

#### Step B — improve sensing only as far as the actual board supports

1. Keep the sensor input adapter as the sole owner of GPIO sampling. Return one immutable sample per control tick, including per-channel digital states and an explicit confidence/validity classification; debounce only short electrical chatter with bounded, measured hysteresis so real narrow lines are not erased.
2. If the exact HW-871 variant provides usable analog outputs, consider per-channel min/max calibration and a normalized reflectance-weighted centroid. Verify the output voltage and ESP32-S3 ADC-capable pins for the installed module before wiring or changing the pin map. If it is digital-only, document the limit and use per-channel potentiometer adjustment plus controlled surface/height testing; do not claim software reflectance calibration from five bits. If contrast still fails on the intended track, evaluate an analog/RC reflectance array as a hardware option.
3. Preserve last reliable line side/position separately from the current sample; do not replace an invalid/no-line sample with a false center position. Keep calibration/diagnostic mode motor-disabled and secrets/network-independent.

#### Step C — stabilize ordinary tracking before adding smarter corner logic

1. Verify coordinate sign, sensor ordering, wheel direction, and center alignment first. Add independent left/right base trim only if the measured straight-line wheel response needs it.
2. Establish a conservative base speed. Tune from a P/PD baseline with `Ki=0`; increase `Kp` until correction is responsive, then add/tune a filtered derivative to damp measured overshoot. Use the exact sensor scale and measured `dt`. Avoid tuning gains and base speed simultaneously.
3. Low-pass the derivative (or derivative-on-measurement), bound output slew if the measured chassis requires it, and make saturation handling explicit. Add a small conditional/leaky integral with anti-windup only if a repeatable steady bias remains after sensor centering and motor trim. Reset or bumplessly transfer controller history only on deliberate transitions, not on one bad sample.
4. Reduce cruise speed as absolute line error/curvature grows, within validated motor bounds, so tight curves do not demand the same speed as straights. Keep the 10 ms control loop local and independent of MQTT/storage; verify worst-case jitter on device.

#### Step D — replace the corner/loss heuristic with explicit, testable states

1. Introduce explicit states such as `TRACK`, `CORNER_CANDIDATE`, `TURN_SEARCH`, `REACQUIRE`, `LINE_LOST`, and `FAULT_STOP` (names can differ). Define for each state its accepted sensor evidence, entry/exit conditions, timeout, motor action, emitted event, and safe failure behavior.
2. In `TRACK`, use calibrated line position/confidence and retain a short history. In `CORNER_CANDIDATE`, require a stable pattern/edge sequence over multiple samples and latch a direction from recent reliable line motion or a configurable route policy. Distinguish a broad straight line/intersection from an actual turn; do not trigger a pivot solely because three adjacent sensors were active.
3. In `TURN_SEARCH`, use reduced bounded pivot/sweep speed and a search direction from the latched corner/last-seen side. Reacquire only after several consistent samples with plausible position progression; reset derivative state and ramp back to tracking rather than accepting a single noisy bit. If no line returns within a measured safe time/distance, enter `FAULT_STOP`. If the course needs deterministic headings beyond 90 degrees, add encoder/IMU feedback or explicitly accept timed-turn variability.
4. Make `Hold`, `Coast`, `Brake`, and `Stop` distinct semantics in the control output and motor adapter. Choose line-loss behavior from measured stopping distance and track hazards; no stale PWM may be held under a state called “coast.” Permit automatic search only in a safe test course; use a stop/fault state near edges or when sensor validity is uncertain.
5. Decide the required intersection/branch policy (continue, left-first, right-first, or route input) before implementation. Do not silently infer user intent from the PID state.

#### Step E — regression tests and physical acceptance

1. Add hardware-independent sequence tests for: stable straight masks; single-sample and repeated sensor dropouts; threshold chatter; broad line; line gap; left/right 45-, 90-, and >90-degree turns; intersection; noisy/false corner cluster; line reacquisition; pivot timeout; invalid sensor state; and `millis()` wrap. Assert bounded motor outputs, no pivot from a straight wide line, no stale command during `Stop`, and no false `Lost` while valid line evidence persists.
2. Record baseline versus new median/RMS line error, correction/PWM saturation fraction, line-loss count, turn success and worst-case `dt`. Set numerical improvement limits from the baseline and actual track; do not invent universal gain values. Physical acceptance should include repeated left/right tests on both intended surfaces at low speed before raising speed, with wheels lifted for sensor/motor diagnostics and a physical power cutoff available.
3. Keep software and physical gates separate: native tests and ESP32-S3 build validate logic/compilation; only the robot can validate optical contrast, comparator threshold, motor symmetry, turn radius, stopping distance, PWM response and timing under real Wi-Fi/power load.

### 7.4 Immediate interpretation of the reported symptoms

- A white surface with a black line is a normal reflectance-sensor use case, but “white” and “black” in visible light do not guarantee sufficient contrast at the sensor's IR wavelength. First check the sensor mask over the actual line/background and tune/measure the physical sensor setup; changing the FSM before this check can only hide a sensing failure.
- The 50-cycle hold-then-stop behavior remains unchanged pending a measured stopping-distance test. `Hold` now reports the previously commanded PWM accurately, but the robot still actively retains that command during the grace interval; it is not coast or line-search behavior.
- The corner FSM now confirms edge clusters and blackout/reacquisition across multiple samples, and rejects ambiguous center clusters. It still uses a fixed-speed timed pivot without heading feedback; success on >90-degree turns is not established.
- The derivative filter and anti-windup are software improvements, not proof that the reported oscillation or straight-line offset is fixed. Sensor threshold, polarity, motor trim and speed scheduling still need measured track data.
